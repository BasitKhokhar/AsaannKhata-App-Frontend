Architecture pressure points

Some domain rules live in screen-local calculations; the customer picker renders all matched customers into a sheet; the New Bill cart uses a ScrollView; and later bill payments are encoded in free-text notes because the backend has no bill-payment relation. The app also lacks a recovery path when SQLite migration fails.

4. Prioritized findings

Critical

F1. Later bill payments do not settle the backend Bill row

The frontend links a customer-payment ledger entry to a bill through a note and derives the displayed due. The sync contract only pushes the customer payment; backend Bill remainingDue, totalReceived and status can stay at checkout values. Server reports and any backend consumer can disagree with the app.

Remedy: add a first-class bill-payment relation and idempotent payment operation on the backend, then migrate the client, sync and reporting paths together.

settlement repositorysync pushdocumented contract

Critical

F2. A sale can record more stock out than existed

Sale stock deductions use Math.max(0, available − sold). A bill can therefore log the full sold quantity while inventory silently stops at zero. This hides shortages and makes the stock audit trail disagree with available stock.

Remedy: choose an explicit oversell policy, validate every line inside the sale transaction, and reject or clearly record approved negative stock. Test all four stock modes and concurrent sale attempts.

High

F3. Shared device data is not fully isolated by account

The app uses one local SQLite database and retains records when the session clears. Cached shops and coin snapshots have account guards, but the documented architecture says full SQLite/device isolation remains unfinished. A production handoff between different shop owners needs a tested data boundary.

Remedy: scope local records to the authenticated owner or use separate databases per account; exercise logout, login, offline and shop-switch scenarios.

database clientsession storeknown limitation

High

F4. Financial and sync regressions have little automated coverage

There are no package lint, typecheck or test scripts and no CI workflow in this repository. Two focused multi-shop sync tests pass, but bill settlement, inventory modes, migrations and offline-to-online reconciliation do not have a release gate.

Remedy: add focused repository/contract tests, static checks and CI before release; include migrated-install and two-device acceptance runs.

High

F5. General customer payments can diverge from bill status

The standalone customer-payment hook subtracts a parsed amount from account balance without allocating it to an invoice or guarding against overpayment. Records continues to show that invoice pending because it only recognizes bill-linked payments.

Remedy: define allocation rules (selected bill or oldest due), validate against account balance, and maintain one payment ledger that drives both customer and bill summaries.

standalone payment hookbill allocation

High

F6. A migration failure has no customer recovery screen

Startup waits for migrations and throws the error if they fail. That protects consistency but can leave the user outside the app without a safe retry/export/support path.

Remedy: provide a non-destructive recovery screen and a tested restore procedure; never auto-delete the local database.

Medium

F7. POS product selection and measurement are limited

New Bill opens a searchable list in a sheet. Area defaults to one sheet and length to 100 cm; the cart only provides steppers for quantity and packs. There is no scanner, volume unit or mode-specific edit sheet in the reviewed UI.

Remedy: use a virtualized catalog grid, per-mode entry sheet, and editable checkout lines. Add volume/barcode only for target shops that need them.

Medium

F8. Production telemetry and endpoint controls need hardening

Sentry initializes, but no explicit event or breadcrumb scrubbing policy is visible. The API URL falls back to an emulator HTTP address if production configuration is missing. These are configuration risks; this scan does not prove that a token has leaked.

Remedy: reject missing/HTTP release endpoints, review telemetry payloads, and configure redaction for auth headers and customer data before enabling release builds.

5. Production release plan

Gate 1 · correctness

Make money and stock authoritative

  1. Introduce a backend bill-payment operation with idempotent client IDs, ledger history and server status updates.
  2. Specify and enforce oversell policy for quantity, area, length and packs.
  3. Unify standalone and bill-linked customer payment allocation.
  4. Test pending → partial → paid, overpayment, refunds/void decisions, offline replay and two-device conflicts.
Gate 2 · protection

Protect shops and release builds

  1. Prove per-account local data isolation after logout/login and offline switch.
  2. Add migration recovery without deleting records.
  3. Require a valid HTTPS API endpoint and review telemetry data handling.
  4. Certify purchases, rewarded ads, push and receipts on release-mode devices.
Gate 3 · quality and growth

Make releases repeatable

  1. Ship lint, tests and CI around repositories and sync contracts.
  2. Profile a 1,000-product shop, long histories and memory use on a low-end Android device.
  3. Improve POS browsing, quantity sheets and accessible target sizes.
  4. Add staff roles, barcode/volume and printer hardware only against verified shop requirements.

Minimum acceptance: no bill or stock write can silently disagree with its audit trail; cross-device balances and status converge; different accounts cannot read each other's offline records; release builds have passing automated and device checks.

Not verified: app startup on Android/iOS, visual/accessibility behavior, actual network and backend deployment, data migration on an installed device, security penetration testing, payment-store sandbox behavior, backend report correctness, and load performance. Scores should be updated after those checks.
