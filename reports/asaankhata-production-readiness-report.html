AsaanKhata production-readiness audit

Frontend + backend · 24 October 2026 · Current, uncommitted worktrees

An evidence-based review of structure, security, billing, offline data, multi-shop sync, monetization, quality, and launch operations. The supplied BK SCAN PRO HTML was used as a report-format/checklist reference only; its instructions and findings were not applied to this project.

1. Executive decision

Not ready for public production release. The app has a coherent offline-first foundation and genuine multi-shop support, but the confirmed P0 findings below can affect data correctness, privacy/store approval, or business rules. Passing unit tests cannot prove that billing, sync, payments, and recovery are safe on real devices and deployed infrastructure.
Architecture: partial One SQLite file with shop-scoped rows; backend has shop ownership middleware and useful indexes. Account-scoped local storage is unresolved.
Data integrity: blocked Client-supplied bill amounts are accepted by the server; sync conflicts overwrite server data; monetary values use floating point.
Store/privacy: blocked “Delete Account” only signs out; legal pages are placeholders; purchase configuration must be verified in production.
Verification: insufficient 2 frontend and 11 backend focused tests pass. No device, full API integration, load, backup/restore, or store-submission evidence was available.

Scope: AsaannKhata-App-Frontend (Expo 57 / React Native / SQLite) and sibling Backendd (Express / Prisma / MySQL), including their current uncommitted changes. Static inspection and non-mutating tests only. No production database, server, app-store console, real device, user data, or signing credentials were accessed. This is not a certification that every flaw has been found.

ServerExpress route → auth/tenant middleware → controller/service → Prisma/MySQLSeparation is workable; validation, limits, error contracts, and observability are inconsistent.
Release/toolingExpo/EAS config, Prisma/Drizzle migrations, focused Node testsMissing CI gates, broad automated coverage, staged rollout evidence, and documented recovery runbooks.

Multi-shop answer: a separate SQLite database per shop is not necessary. The existing single-database design can scale to many shops when every query, mutation, foreign-key check, index, sync cursor, and cache key is correctly scoped by shopId and account ownership. The current code already syncs every server-owned shop, not just the selected shop. Do not claim an arbitrary row-count guarantee: measure on low-end target devices with realistic month/year datasets.

3. Findings, ordered by launch impact

ID / priorityFinding and evidenceImpactRequired action / acceptance test
F01 · P0Server trusts bill totals, discount, amount received, remaining due, and line totals from requests rather than recomputing and validating them. Both direct creation and offline push do this: billingControllers.js:5–56, syncService.js:272–340.A malformed or tampered request can create inconsistent sales, customer debt, and stock history.Define one server-side bill-calculation/validation contract, reject negative/non-finite values and mismatched totals, snapshot sale-time price/cost, and test direct + sync routes with malformed inputs.
F02 · P0Sync detects an older base timestamp but still updates the server row, then returns conflict: syncService.js:142–147, 212–214, 411–416, 504–506.Concurrent edits from another device may be overwritten before the user can resolve them.Reject conflicting writes before mutation, keep both versions, surface resolution UI, and test two-device concurrent changes per entity.
F03 · P0Settings’ “Delete Account” confirmation calls logout only; backend exposes no owner deletion flow: Settings.jsx:88–100. Legal links say “coming soon”: About.jsx:54–100.User expectation is misleading; account/data deletion and required disclosures are absent. Both Google Play and Apple require an account deletion path for apps that create accounts.Implement authenticated deletion request/fulfilment, local cleanup and retention notice; publish functioning Privacy Policy/Terms and truthful consent. Verify store listings and deletion URL.
F04 · P0Permanent ad-supported free access requested for this product is not implemented. Registration activates an expiring FREE_TRIAL; expired entitlement has canWrite: false: authController.js:59, subscriptionService.js:10–70. Local bill writes explicitly ignore entitlement: billRepository.js:10–20.Plan behavior differs from intended offering, and online/offline limits can disagree. The advertised backend daily limit is not itself a durable free-plan entitlement.Approve a written plan matrix, then implement server-authoritative quota/shops/devices limits with offline allowance reconciliation and abuse cases. Test expired, free, lifetime, and subscription transitions.
F05 · P0POST /ads/reward grants coins when called by any authenticated client, based on a daily counter, with no server-verifiable ad-completion proof: adsRoutes.js, adsController.js:73–115.An altered client can call the endpoint without watching an ad and mint up to the daily cap. If coins unlock sync, this undermines the plan rules.Design a verifiable rewarded-ad grant path (provider server-side verification or equivalent authenticated receipt), bind unique ad events, and test replay/concurrency.
F06 · P0One persistent SQLite file is opened for all sign-ins and deliberately retained on logout: client.js:7, Settings.jsx:75–85. Shop list queries filter by admin, but data retention/account-switch isolation is not comprehensively enforced or tested.On a shared device, old business data remains on disk; stale IDs/cache paths could expose or mutate another account’s local rows. This is a confirmed retention issue and an unproven cross-account UI exposure risk, not a demonstrated exploit.Choose account-keyed DBs or rigorously scoped owner columns + verified account-switch purge/lock; test A→logout→B offline, account deletion, token expiry, and recovery.
F07 · P1Neither API nor product/category/shop upload middleware sets a visible size cap; express.json() is default-configured and images use in-memory Multer: app.js:23–25, productRoutes.js:10, shopsController.js:6. No rate-limiter appears in route/app setup.Abuse can exhaust memory or password-guessing capacity. Default JSON body limit is not a substitute for explicit endpoint-specific policy.Set image MIME/size constraints, request/body limits, auth/ads rate limits, and trusted proxy/CORS policy; verify with boundary and abuse tests.
F08 · P1Direct bill creation and stock changes accept non-positive/invalid quantities in several paths, and backend stock decrements are not shown to guard against negative stock: billingControllers.js:54–56, billStockService.js:12–49. Local sales clamp at zero instead: billRepository.js:99–116.Local and cloud stock can diverge, especially with simultaneous or oversold transactions.Specify oversell policy; validate units/quantities and enforce atomically on server. Reconcile local/server counters in multi-device tests.
F09 · P1Currency and balances use Prisma Float and SQLite real-number arithmetic: schema.prisma:259–264, 403, 432, 456.Binary floating-point rounding can cause receipt, balance, and profit discrepancies.Use integer minor units or defined decimal precision end to end; add rounding, refund, discount, and large-value tests before migration.
F10 · P1Historical profit joins sold items to the product’s current purchase price: analyticsRepository.js:19–32, 57–65.Editing today’s cost changes past profit reports. Area/length conversion is also marked approximate in the code.Persist cost and unit conversion at sale time; backfill or explicitly label historical estimates; test price changes.
F11 · P1Several local repositories read every shop row using .all(), and expense/customer history screens map those arrays in a ScrollView: createSyncableRepository.js:15–24, billRepository.js:128–152, Expenses.jsx:97–113, CustomerDetail.jsx:42–84. Server bill/product limits are unbounded client inputs: billingControllers.js:109–111, productsController.js:129,158.Large shops may see slower screens, high memory, and oversized API responses.Add indexed cursor/limit pagination, virtualized lists, bounded backend limits, and benchmark 10k/100k+ rows on a low-end device.
F12 · P1Pull protects pending/conflict rows in pull.js:10–24, but generic createSyncableRepository.js:90–110 still overwrites an existing pending row if that helper is used for server upsert. Current sync uses pull.js; this is a latent unsafe API, not a confirmed current overwrite.Future use of the generic method can silently drop local edits.Make the repository helper enforce the same pending/conflict guard and add a regression test.
F13 · P1Registration and refresh issue 15-day access and 180-day refresh JWTs; refresh stores only one token and password update does not revoke it: authController.js:10–15, 123–166.Compromised tokens can stay useful for a long period; password change does not end other sessions.Shorten/rotate access tokens, hash and rotate refresh tokens, revoke on logout/password/reset/account suspension, test device sessions.
F14 · P1The app throws the migration error at startup without a recovery/export screen: App.jsx:102–108. Android auto-backup is disabled: app.config.js:41. Offline/lifetime data therefore needs an explicit recovery strategy.A failed migration, lost phone, or reinstall can make unsynced data unavailable.Build tested migration rollback/retry, encrypted export/restore or clearly documented cloud backup limitation, and upgrade tests from every shipped schema.
F15 · P1Production config falls back to Android-emulator URL http://10.0.2.2:5000 if API setting is absent: app.config.js:9–10. Purchases require runtime SDK keys: revenueCat.js:14–23. Actual EAS environment values/build artifacts were not accessible.A build can look successful but ship with no reachable backend or broken purchases.Fail production builds on missing HTTPS URL, RevenueCat/AdMob IDs, EAS project, webhook secrets, and test purchase/restore/refund on both stores.
F16 · P1Additional-shop creation has no plan-specific maxShops rule: shopRoutes.js:8–13, shopsController.js:10–43. Plans currently contain max devices but not max shops: schema.prisma:482–500.The proposed multi-shop subscription tiers cannot be enforced correctly.Add explicit max shops/active shops entitlement and atomic quota check; cover concurrent shop creation and downgrade policy.
F17 · P2Accessibility labels are sparse outside a few shared controls; translation/RTL is partly manual, and some strings visibly render as mojibake in source/terminal: BottomNav.jsx:31–33, Settings.jsx:43–47.Screen readers, Urdu/Hindi readability, dynamic type, and navigation usability need proof on devices.Audit all interactive elements, 200% text, contrast, touch targets, VoiceOver/TalkBack, RTL, and locale/date/currency formatting.
F18 · P2Backend mostly logs to console and returns raw err.message from many 500s (for example billingControllers.js:98,139); mobile initializes Sentry but no release monitoring evidence was available.Errors can leak internal details and production incidents may be hard to trace.Centralize sanitized error responses, request IDs, structured logs/metrics, alerting, and privacy-safe crash reporting.
F19 · P2Shop deletion is a direct hard delete: shopsController.js:122–136. No export/retention/undo flow is visible.Business records can be irrecoverably lost or deletion may fail on relational constraints.Define archive/soft-delete policy, confirm/export before deletion, and test restore and legal retention.

5. Prioritized release roadmap

  1. Product decision first: finalize plan entitlements (free forever versus trial, ad-earned daily bills, lifetime offline, monthly/yearly cloud, max shops/devices, downgrade behavior). Record exact backend-authoritative rules and offline reconciliation rules.
  2. Integrity and safety: fix F01–F03, F05–F06, F08–F10; write adversarial API and two-device sync tests before data migration. Decide whether historical money data needs conversion/backfill.
  3. Reliability and scale: fix F07, F11–F14, F16; test 100k+ records across multiple shops, interrupted sync, reinstall, account switching, and all prior SQLite schema upgrades.
  4. Launch proof: resolve F15, F17–F19; test signed Android/iOS builds, real ads/IAP sandbox flows, webhooks, notification permissions, accessibility, legal documents, deletion, and restore.
  5. Release gates: CI green; no unresolved P0; P1 risks accepted in writing only if non-data-loss; staging migrations and rollback rehearsed; production config validated; store policy checklist completed; pilot rollout monitored with crash/error/financial reconciliation metrics.

6. Verification performed and limits

  • Passed: node scripts/multiShopSync.test.cjs — 2/2; npm.cmd test --prefix ..\Backendd — 11/11; backend local prisma validate — schema valid.
  • Not verified in this audit: deployed Prisma migrations, real MySQL/API integration, signed EAS builds, store review, device performance, real billing/ads, push notifications, disaster recovery, security penetration testing, accessibility on-device.
  • Tooling constraint: local drizzle-kit check failed with host uv_os_get_passwd ENOMEM; this is not evidence of a migration defect. Re-run it in CI. The initially attempted npx prisma command tried to fetch from a restricted registry; the installed backend Prisma CLI validated successfully instead.
  • Config handling: local .env files exist but their values were not included in this report. This audit did not verify whether live credentials are correctly configured.
